⚖️ Architectural Analysis: WSO2 Internal Database Sync vs. eID REST API Verification

In Pattern 2B, when a citizen eID application is approved at PSC, their credential record is pushed via API into WSO2's internal userstore DB. During login, WSO2 verifies credentials directly against its local database rather than calling the eID API.

👍 Advantages of WSO2 Database Sync
  • Zero External REST Latency at Auth Time: WSO2 checks credentials locally in its own database without an outbound HTTP REST call to eID Core.
  • Network Isolation Resilience: If network connectivity between WSO2 and eID Core drops temporarily, existing provisioned citizens can still log in.
  • Standard WSO2 Native Pattern: Operates natively using WSO2's out-of-the-box LDAP / Userstore manager.
👎 Disadvantages & Risks (Why Pattern 2A REST API is Preferred)
  • ⚠️ Data Stale & Revocation Lag: If an eID is revoked or suspended in eID Core, there is a sync lag before WSO2 DB updates, allowing revoked users to log in!
  • ⚠️ Duplicate Credential Vault & Security Risk: Password hashes and user attributes are duplicated across two databases (eID Vault + WSO2 DB), doubling attack surface area.
  • ⚠️ FIDO2 WebAuthn Passkey Limitation: WSO2's standard database userstore cannot natively validate hardware WebAuthn FIDO2 passkeys (Apple TouchID, YubiKey) without calling eID WebAuthn vault.
  • ⚠️ Annex E Audit Compliance Complexity: Splitting identity state between WSO2 DB and eID DB violates the single-source-of-truth compliance standard.
Phase 1: Provisioning
1. Citizen Enrolment & WSO2 DB Sync
Citizen completes PSC / Online Enrolment. Upon approval, eID Platform generates eID Credential and immediately calls WSO2 API (POST /api/server/v1/users) to push user record into WSO2 DB.
Phase 2: Auth Request
2. RP Redirects to WSO2 Hosted Form
Citizen clicks "Login" on Relying Party (COCI). RP redirects citizen to WSO2 IS 7.0 Hosted Login Page (https://localhost:9443/oauth2/authorize).
Phase 3: Verification
3. WSO2 Local DB Credential Check
Citizen inputs eID Serial / Email & Password into WSO2 Hosted Form. WSO2 queries its internal database userstore locally to verify credentials.
Phase 4: Token Return
4. WSO2 MFA & Token Return
WSO2 executes 2FA OTP, issues OIDC ID Token & Access Token containing Pairwise Pseudonym (PPID), and redirects back to Relying Party (COCI).
🔄 End-to-End Sequence & Data Flow (Pattern 2B)
WSO2 DB Sync Verification Architecture
1

eID Provisioning Sync Call (`eID Core` → `WSO2 DB`)

When PSC agent approves citizen enrolment, eID Platform issues `eID` and triggers background webhook `POST https://localhost:9443/api/server/v1/users` to create citizen user in WSO2 Userstore DB.

2

RP Login Initiation (`COCI App` → `WSO2 Form`)

Citizen initiates login on RP1 (COCI). COCI redirects browser to WSO2 IS 7.0 Hosted Login UI with OIDC `client_id=client_coci_sm_prod` & PKCE `S256` parameters.

3

WSO2 Local Database Credential Verification (`WSO2 UI` → `WSO2 Internal DB`)

Citizen enters eID Serial / Email and Password on WSO2 Hosted Form. WSO2 verifies password hash directly against `wso2_db.UM_USER` table without calling eID API.

4

WSO2 MFA & OIDC Token Return (`WSO2` → `COCI App`)

WSO2 prompts for 2FA OTP code. Upon success, WSO2 generates OIDC authorization `code`, exchanges for ID Token & Access Token with Pairwise Pseudonym (`ppid_coci_...`), and returns user to COCI.
