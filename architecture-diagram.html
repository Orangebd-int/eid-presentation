Sint Maarten eID High Level Architecture

Core Architecture Rules & Platform Activities Matrix

🪪 Rule 1: Login Credentials (eID & Email Only)

Citizens log in strictly using their eID Number (`EID-SXM-26-XXXXXX-C`), Email Address, or FIDO2 Passkey.

UIN (Unified Identity Number) is strictly an internal database identifier for Civil Registry / Pairwise identity management and is never used or requested on public login screens.

⚡ Rule 2: Key2Data & Civil Registry Call Policy

All routine authentication, token issuance, and single sign-on (SSO) requests are handled 100% locally by the eID Platform (PostgreSQL & Redis cache).

The eID Platform calls Key2Data → Civil Registry only when demographic updates or initial enrolment verification is required, ensuring sub-50ms login performance.

🌐 WSO2 Identity Broker Activity

Acts as the central OIDC federation broker & gateway. Manages Relying Party client registrations, validates OAuth2 PKCE parameters, issues pairwise pseudonymous claims (PPID), and enforces OIDC Back-Channel Single Logout (SLO) across all RP applications.

🔐 Sint Maarten eID Platform Activity

Acts as the core Identity Provider (IDP) and credential vault. Handles citizen FIDO2 WebAuthn passkeys, 2FA OTP verification, Annex E audit logging, eID lifecycle state enforcement (`active`, `pre_provisioned`, `under_review`, `revoked`), and high-performance local caching.

⚖️ Pattern 1 Evaluation: Advantages & Trade-offs (eID Federated Login UI + Native WebAuthn Passkeys)

In Pattern 1, WSO2 acts as the central OIDC Broker, while the citizen login form is hosted directly on the Sint Maarten eID Platform, enabling native WebAuthn FIDO2 biometric authentication (Apple TouchID, Face ID, YubiKeys).

👍 Key Advantages (Pros)
  • ✓ Native WebAuthn & FIDO2 Hardware Passkeys: Citizens log in seamlessly using Apple TouchID, Face ID, or hardware security keys directly on the eID domain (id.gov.sx).
  • ✓ 100% Brand Consistency & Citizen Trust: Citizens always see the official, verified Sint Maarten government login interface, eliminating phishing risks.
  • ✓ Instant eID Lifecycle Enforcement: State checks (active, revoked, suspended) are evaluated directly in local memory before issuing tokens.
  • ✓ No WSO2 Login Template Customization Required: WSO2 handles OIDC broker federation in the background; zero UI customization is needed inside WSO2.
  • ✓ Centralized Zero-Trust Credential Vault: Citizen password hashes, FIDO2 keys, and recovery seeds never cross server boundaries, guaranteeing eIDAS High security isolation.
  • ✓ Simplified WSO2 Version Upgrades: WSO2 acts strictly as a lightweight OIDC Broker & Protocol Gateway. Upgrading WSO2 IS versions requires zero changes to citizen login UI or auth logic.
  • ✓ Flexible Multi-Factor & Step-Up Auth: eID Core can enforce dynamic step-up biometrics for high-assurance services without modifying WSO2 configuration.
⚖️ Architecture Trade-offs (Cons & Constraints)
  • ⚠️ Additional Browser Redirect Hop: Citizen browser redirects: RP App → WSO2 Broker → eID IDP Form → WSO2 Broker → RP App.
  • ⚠️ Requires Outbound OIDC Federation Setup: WSO2 IS must be configured with an outbound Federated Identity Provider entry pointing to the eID OIDC endpoints.
🚀 Relying Party (RP) Onboarding for SSO (Pattern 1 Workflow)
US-6.1 • US-6.2 • US-6.3 Compliant
🔑 Key Architecture Rule for RP Onboarding: Every Relying Party (COCI, Tax, Health) connects directly to WSO2 IS 7.0 (The Identity Broker), NOT directly to the eID Platform. WSO2 manages OAuth2 client_id credentials, redirect URIs, OIDC token issuance, and Pairwise Pseudonyms (PPID), while federating authentication to the Sint Maarten eID Core Provider.
Step 1 • US-6.1

Developer Sandbox Onboarding

RP Developer registers their application on the eID Developer Portal (/admin/sandbox), defining redirect URIs and requesting claims without needing platform team intervention.

Step 2 • OIDC Provisioning

WSO2 Broker Sync

Developer Portal automatically registers OAuth2 Client Credentials in WSO2 IS 7.0 OIDC Broker & configures federated IDP redirect rules.

Step 3 • US-6.2

Realistic Test Identities

RP tests authentication & error handling against 4 distinct sandbox states: active, pre_provisioned, under_review, and revoked.

Step 4 • US-6.3

Automated Conformance Test

Automated test suite executes per-check pass/fail audit covering PKCE (S256), pairwise pseudonyms (PPID), and OIDC Back-Channel Logout before production sign-off.

01

Step 1: RP App Initiates OIDC Authorization Request

GET /oauth2/authorize?client_id=coci-rp&response_type=code&scope=openid+profile

The citizen visits a Relying Party application (e.g. COCI Portal or Tax Portal) and clicks "Sign In with Sint Maarten eID". The RP App generates a PKCE code verifier and code challenge, then redirects the browser to the WSO2 IS 7.0 Identity Broker.

02

Step 2: WSO2 Identity Broker Federates Request to eID IDP

GET /oauth/authorize?client_id=eid-wso2-broker-client-id

WSO2 IS 7.0 validates the Relying Party registration and scope permissions. WSO2 federates the authentication challenge directly to the Sint Maarten eID Core Provider (`/oauth/authorize`).

03

Step 3: eID Engine Authenticates Citizen Credentials (eID / Email)

POST /api/v1/auth/verify-credentials

The citizen enters their eID Number (`EID-SXM-26-XXXXXX-C`) or registered Email Address. The eID Platform checks local cached credentials & identity status (`active`, `pre_provisioned`, `under_review`, `revoked`).

04

Step 4: Key2Data → Civil Registry Sync (Triggered On-Demand Only)

POST /api/v1/key2data/civil-registry/verify-bsn

Operational Rule: Day-to-day citizen logins are processed locally by eID Platform for maximum speed. The eID Engine calls Key2Data → Civil Registry only during initial enrolment or when demographic profile updates are required.

05

Step 5: 2FA & FIDO2 WebAuthn Verification

POST /api/v1/mfa/verify-passkey

The citizen completes 2-Factor Authentication using FIDO2 Apple Touch ID / Face ID, YubiKey 5 NFC hardware token, or 6-digit SMS OTP, satisfying eIDAS Level High cryptographic assurance.

06

Step 6: Token Exchange & Pairwise Claims Return to RP App

HTTP 302 Redirect to RP App /callback?code=AUTH_CODE

The eID Engine issues an authorization code to WSO2 Broker. WSO2 exchanges the code for signed JWT ID & Access Tokens containing Pairwise Pseudonymous Identifiers (PPID) and returns the citizen securely to the RP App!
